# Use React Aria Components behind a Breeze-owned API

The v4 decision affirms React Aria Components (RAC) as Breeze UI's default behavioural foundation for interactive components. React Aria remains an internal implementation detail: Breeze defines and documents its own public component APIs and translates them into RAC APIs so dependency changes do not propagate directly to consuming applications. Breeze will not re-export RAC components or types, derive public props from RAC components, or provide a generic RAC prop pass-through; required behaviour must enter through an intentional Breeze API while relevant native platform attributes and refs remain available. The styling API is closed: components do not accept `className`, `style`, slot props, render props, or other styling or component pass-through.

The v4 specification defines five hand-built exception categories: `Toast`, nested overlay geometry, integration at the private PressResponder boundary, non-interactive primitives, and optional hand-building of `AppearanceControl`. These are ownership boundaries, not a claim that every category currently has bespoke code: the source tree has no authored PressResponder module or `react-aria/private` import, and `AppearanceControl` currently uses RAC's `ToggleButtonGroup` and `ToggleButton`. Breeze owns any required composition at the private boundary without exposing it as public API. The specification calls for `Toast` to be a single `role="status"` card without dismiss, avoiding v3's unstable toast APIs; primitives with no interaction behaviour need no RAC interaction layer.

## Overlay ordering boundary

For `Dialog`, `Drawer` and `Popover`, Breeze deliberately owns a hand-built nested overlay stack, as required by [issue #1602](https://github.com/motech-development/platform/issues/1602). The prototype's sheet, non-modal contextual panels and full-screen overlay establish the required compositions: a popover leaves the sheet interactive and accessible, while a full-screen surface covers the sheet without unmounting it. Both preserve the sheet's scrim and dismiss the topmost surface first with Escape. Nested confirmation dialogs are not the basis for this boundary; the public centred `Dialog` remains available as a neutral modal primitive.

React Aria continues to own focus scopes, ordinary focus restoration, modal interaction behaviour and the entering/exiting lifecycle. Breeze places initial focus in non-modal labelled sections without activating a dialog focus trap, and handles popover outside clicks after the sheet's pointer gesture has completed to prevent dismissal from cascading. Breeze owns surface ordering, parent/child relationships, exclusion of closing surfaces and their descendants from the active stack, and scrim ownership. A nested non-modal popover neither traps focus nor hides the underlying sheet from assistive technology. `DocumentViewer` uses the internal `OverlaySurface` as a full-screen modal dialog (`kind="dialog"` with `fullScreen`); this is an implementation detail, not a new public component. Closing it restores focus to its trigger in the still-mounted sheet. Breeze also restores the owning trigger if simultaneous nested exits leave focus on the document body after React Aria cleanup; it does not replace ordinary focus handling or steal focus from another active surface.

This narrow exception is covered by the standing `Foundations/Overlay stack` regression suite in `src/overlays/OverlaySurface.stories.tsx`: `SheetPopover`, `SheetFullscreen`, `CloseOuterFirst` and `InitiallyNested`. It checks nested opening, topmost-first Escape dismissal, outer-first closing, focus restoration, underlying sheet accessibility and preservation of the sheet's scrim. Overlays use the provider's marked portal host and library CSS driven by the kit's lifecycle attributes, respect reduced motion, and never participate in view transitions.
