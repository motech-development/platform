# Use React Aria Components behind a Breeze-owned API

The v4 decision affirms React Aria Components (RAC) as Breeze UI's default behavioural foundation for interactive components. React Aria remains an internal implementation detail: Breeze defines and documents its own public component APIs and translates them into RAC APIs so dependency changes do not propagate directly to consuming applications. Breeze will not re-export RAC components or types, derive public props from RAC components, or provide a generic RAC prop pass-through; required behaviour must enter through an intentional Breeze API while relevant native platform attributes and refs remain available. The styling API is closed: components do not accept `className`, `style`, slot props, render props, or other styling or component pass-through.

The v4 specification defines five hand-built exception categories: `Toast`, nested overlay geometry, integration at the private PressResponder boundary, non-interactive primitives, and optional hand-building of `AppearanceControl`. These are ownership boundaries, not a claim that every category currently has bespoke code: the source tree has no authored PressResponder module or `react-aria/private` import, and `AppearanceControl` currently uses RAC's `ToggleButtonGroup` and `ToggleButton`. Breeze owns any required composition at the private boundary without exposing it as public API. The specification calls for `Toast` to be a single `role="status"` card without dismiss, avoiding v3's unstable toast APIs; primitives with no interaction behaviour need no RAC interaction layer.

## Overlay ordering boundary

For `Dialog`, `Drawer` and `Popover`, Breeze deliberately owns a hand-built nested overlay stack, as required by [issue #1602](https://github.com/motech-development/platform/issues/1602). The prototype's sheet, non-modal contextual panels and full-screen overlay establish the required compositions: a popover leaves the sheet interactive and accessible, while a full-screen surface covers the sheet without unmounting it. Neither is modal, so the sheet beneath stays interactive and keeps the only scrim, and Escape dismisses the topmost surface first. Nested confirmation dialogs are not the basis for this boundary; the public centred `Dialog` remains available as a neutral modal primitive.

React Aria continues to own focus scopes, ordinary focus restoration, modal interaction behaviour and the entering/exiting lifecycle. Breeze places initial focus in non-modal labelled sections without activating a dialog focus trap (the full-screen surface, below, is the one exception), and handles popover outside clicks after the sheet's pointer gesture has completed to prevent dismissal from cascading. Breeze owns surface ordering, parent/child relationships, exclusion of closing surfaces and their descendants from the active stack, and scrim ownership. A nested non-modal popover neither traps focus nor hides the underlying sheet from assistive technology. Breeze also restores the owning trigger if simultaneous nested exits leave focus on the document body after React Aria cleanup, or focuses the still-open parent surface when the trigger left with the closing surface; it does not replace ordinary focus handling or steal focus from another active surface.

## Non-modal document viewer

`DocumentViewer` opens the internal `OverlaySurface` as a non-modal full-screen surface (`kind="fullscreen"`), as the prototype does; this is an implementation detail, not a new public component. It covers the record sheet without making it inert, the sheet keeps its scrim, Escape closes the viewer before the sheet, and closing it restores focus to its opener in the still-mounted sheet. The repository owner chose this, recorded on [issue #1602](https://github.com/motech-development/platform/issues/1602), over the alternative of a modal viewer stacked over the modal sheet, which would have taken the sheet's scrim.

The trade-off was raised before the decision and accepted deliberately: the surface is not modal, so nothing it covers is made inert or hidden from assistive technology. That holds for a viewer opened from the record sheet and for one opened from a plain page; in both cases a screen reader can still read the covered content even though it cannot be seen.

Keyboard focus does not follow. Leaving the covered content reachable must not strand a keyboard user on controls they cannot see, so the full-screen surface contains focus with React Aria's `FocusScope` while it is open. Tab and Shift+Tab wrap inside the viewer, focus that assistive technology moves into the covered content returns to the viewer, and Escape, which the topmost surface receives while focus is inside it, closes the viewer before the sheet. The surface also locks page scrolling while it is open, as React Aria does for modal overlays, because React Aria leaves scrolling unlocked for non-modal popovers: wheel and touch scrolling inside the viewer never moves the hidden page.

## Regression coverage and motion

This narrow exception is covered by the standing `Foundations/Overlay stack` regression suite in `src/overlays/OverlaySurface.stories.tsx` (`SheetPopover`, `SheetFullscreen`, `PageFullscreen`, `FullscreenPopover`, `FullscreenModal`, `CloseOuterFirst` and `InitiallyNested`) and by `src/overlays/OverlaySurface.test.tsx`. Together they check nested opening, topmost-first Escape dismissal, outer-first closing, focus restoration into the sheet, underlying sheet accessibility and preservation of the sheet's scrim, on the same non-modal full-screen path that `DocumentViewer` uses. They also check that full-screen containment keeps Tab and Shift+Tab inside the viewer, including around a nested popover and after a modal above it closes; that a viewer opened from a plain page holds the page's scroll; and that the scroll lock stacks with the drawer's and is released in either closing order.

Overlays use the provider's marked portal host and library CSS driven by the kit's lifecycle attributes, and respect reduced motion. Only the overlay layer element is excluded from view transitions: it is forced to `view-transition-name: none`, so the surface is never captured as a shared element. Content inside an overlay may still take part. `DocumentViewer`'s panel inside the full-screen surface carries a transition name and joins the `expand` and `mode` transitions, including the `expand` morph that opens and closes the viewer. While an `expand` transition is active the full-screen surface skips its own fade, so the morph carries the motion alone; the fade remains whenever no `expand` transition runs.
