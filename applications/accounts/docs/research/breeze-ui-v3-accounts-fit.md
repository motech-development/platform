# Breeze UI v3 fit and composition gaps for Accounts

## Research question

Against [Inventory the existing Accounts client compatibility contract](https://github.com/motech-development/platform/issues/1525) and [Shape the replacement application shell and information architecture](https://github.com/motech-development/platform/issues/1532), which required Accounts UI capabilities can reuse Breeze UI v3, which belong in `@accounts/web`, and which reveal a domain-neutral Breeze gap?

This note resolves [Audit Breeze UI v3 fit and composition gaps for Accounts](https://github.com/motech-development/platform/issues/1539). It audits the repository at commit `5c1ca8f0f08a32274642c6b931af2b6c8fee8996`, the same compatibility baseline named by the inventory.

## Result

Breeze UI v3 is a strong fit for the replacement. Its public API already covers the shell, semantic navigation, company context switcher, page hierarchy, route-driven drawers, accessible form controls, responsive record tables, transaction grouping geometry, feedback, file selection, formatting, and overlay mechanics.

Only two capabilities need a Breeze change:

1. `ApplicationShell` needs a public way for the application to close or control the compact navigation drawer after route navigation.
2. `UserMenu` needs public open-state/dismissal reporting and a count-aware unread accessible-name contract so Accounts can mark the displayed notifications read when the surface closes while preserving names such as `Notifications (3 unread)`.

Everything else that is absent is application behavior or application composition, not a reusable Breeze omission. In particular, form schemas and masks, financial calculations, route state, company switching rules, exact-name deletion, presigned transport, report readiness, and document rendering stay in `@accounts/web`.

This conclusion follows Breeze's own boundary: patterns are recurring domain-neutral compositions, while application meaning remains outside the library (`packages/breeze-ui/src/docs/05-Composition.mdx:41-75`); applications own schemas, submission, cross-field rules, server errors, and business validation (`packages/breeze-ui/src/docs/06-StateAndForms.mdx:8-10`).

## Recommendation key

- **Reuse** — the public Breeze API supplies the required generic behavior. Accounts still owns data, copy, routing, and domain state.
- **Accounts-local composition** — combine public Breeze parts in `@accounts/web`; the missing behavior is domain- or workflow-specific.
- **Breeze addition/change** — a recurring domain-neutral behavior is unavailable through the relevant public pattern and an application workaround would depend on remounts, internal DOM, or incomplete semantics.

## Required Breeze changes

### 1. Compact navigation lifecycle

`ApplicationShell` should expose a public route-aware lifecycle for its compact drawer. The least surprising shape is controlled/uncontrolled state consistent with `Drawer.Root`, for example `compactNavigationOpen`, `defaultCompactNavigationOpen`, and `onCompactNavigationOpenChange`, although the implementation ticket should choose the final API.

Acceptance behavior:

- Accounts can close the compact drawer after an ordinary in-app destination activation or observed route change.
- Modified-click and native anchor behavior remain untouched.
- Escape, explicit close, focus containment, scroll lock, logical start placement, and focus restoration continue to come from `Drawer`.
- The wide rail is unaffected by compact open state.

### 2. User menu lifecycle and unread accessible state

`UserMenu` should expose open-state reporting consistent with `Menu.Root` and allow the application to supply a complete, localized count-aware unread announcement. A generic fallback can remain for callers that only know a boolean.

Acceptance behavior:

- `onOpenChange(false)` is reported once for Escape, outside dismissal, trigger toggle, and action activation.
- Accounts can mutate exactly the IDs displayed when the menu closes.
- The trigger can have the exact accessible name `Notifications (N unread)` while still showing the unread dot.
- Focus and keyboard behavior stay those of `Menu`.
- Updating read state changes both visible count and accessible name without relying on colour.

These two changes should land before the replacement shell is integrated. Both prevent application workarounds against persistent shell state; neither adds Accounts-specific concepts to Breeze.

## Accessibility and responsive constraints

The following constraints apply across every row:

- Breeze targets WCAG 2.2 AA and supplies component semantics/keyboard/focus behavior, while Accounts must provide truthful names, relationships, headings, content, and workflow decisions (`packages/breeze-ui/src/docs/07-Accessibility.mdx:8-41`).
- Preserve the existing smoke-test accessible names. Examples include `Add a new company`, `Add a new client`, `Record a new transaction`, the `Manage …` destinations, upload/view/download controls, and `Notifications (N unread)` (`applications/accounts/client/e2e/vat-registered.spec.ts:20-55`, `:346-417`, `:691-766`).
- Retain Axe coverage at the composition level. The current suite checks selected list, drawer/form, client, and transaction surfaces for zero WCAG 2 A/AA violations (`applications/accounts/client/e2e/vat-registered.spec.ts:20-39`, `:346-357`, `:399-417`), but the replacement still needs keyboard and screen-reader review.
- Use Breeze's mobile-first breakpoints: `sm` 681px, `md` 901px, and `lg` 1181px (`packages/breeze-ui/src/docs/10-StylingAndResponsiveLayout.mdx:26-43`). This directly satisfies compact records through 680px and bottom-sheet placement through 900px.
- Keep authored DOM/focus order meaningful; responsive CSS may rearrange geometry but not reading order (`packages/breeze-ui/src/docs/10-StylingAndResponsiveLayout.mdx:12-24`).
- Do not override component descendants, private data attributes, or private variables from Accounts CSS. `className` is for placement and composition only (`packages/breeze-ui/src/docs/10-StylingAndResponsiveLayout.mdx:45-55`).
- All modal layers require meaningful titles and contextual descriptions. Destructive decisions use `AlertDialog`; ordinary task overlays use `Drawer`/`Dialog` (`packages/breeze-ui/src/docs/07-Accessibility.mdx:29-34`).
- Reduced-motion behavior is already global in Breeze (`packages/breeze-ui/src/styles/base.css:45-53`); Accounts transitions must not reintroduce motion outside that boundary.

## Differences that are not Breeze gaps

The v3 clean-break ADR explicitly rejects compatibility exports and migration shims (`packages/breeze-ui/docs/adr/0001-breeze-ui-v3-clean-break.md:1-4`). Therefore these absences are expected remappings, not missing capabilities:

| Legacy surface or visual | v3 direction | Why it is not a gap |
| --- | --- | --- |
| `Loader`, `Overlay` | `Spinner`, `Skeleton`, labelled busy regions, `Button loading` | Loading behavior is present with stronger explicit semantics. |
| `PageTitle` | `PageHeader` | Page hierarchy and responsive actions are present. |
| `DataTable`, legacy `Table*` | compound `Table` | Structured rows, responsive records, grouping, empty state, actions, sorting, and load-more are present. |
| `TextBox` with prefix/suffix/mask | `TextField`/`NumberField` + `InputGroup`; local schema/normalization | Generic field semantics are present; domain masks and validation belong to Accounts. |
| `Typeahead` | `ComboBox allowsCustomValue` | Free-text commits with suggestions are explicitly supported. |
| `Modal` | `Dialog`, `AlertDialog`, `Drawer` | The required modal behaviors are covered with role-appropriate primitives. |
| Interactive legacy `Stepper` | descriptive `Stepper` + local actions/state | Navigation and validation are workflow behavior, deliberately not owned by the visual progress list. |
| Masonry/card lists and exact prototype spacing | responsive `Table`, `Grid`, `Card`, canonical drawer sizes | These are presentation choices unless an observable capability or accessibility behavior is lost. |
| PDF/document viewer | local renderer inside Breeze overlay/toolbar primitives | Binary decoding, page rendering, and blob lifecycle are application integrations, not design-system behavior. |
