# Retain Exhausted Stream Batches for Balance and Attachment Processing

The `Attachments` and `Transactions` consumers of the application table stream will share one stream-processing failure store instead of discarding a batch after its fifth failed attempt. Each consumer's event source mapping sends the complete failed invocation to an encrypted S3 bucket, and an S3 object-created event is sent through EventBridge to the stream-processing dead-letter queue, whose alarm invokes the existing Sentry-reporting Lambda. S3 is used rather than an SQS destination because an SQS destination receives only shard and sequence metadata, which cannot be recovered once DynamoDB Streams' 24-hour retention has passed. This follows the schedule-synchronisation failure store in ADR 0001 but is kept separate from it so that each dead-letter queue continues to identify one failure boundary and one recovery procedure.

ADR 0004 has since merged these consumers into `ProcessStream` and `PublishStream`, which both use this store. Only `PublishStream` applies Balances, so a `Transactions` batch is now replayed to `PublishStream`, and the replay rules below apply to every batch replayed to it.

A lost `Transactions` batch leaves a company Balance permanently wrong, and a lost `Attachments` batch leaves a deleted Transaction's file in storage. The other stream consumers do not use the store. `PublishNotifications` and `UpdateBalance` only publish live AppSync beacons through a resolver without a data source; the Notification, Balance and Transaction items they announce are already stored, so a missed beacon is recovered by the next read. `Typeahead` maintains derived suggestions, where a missed record costs one suggestion. These consumers retry a failed batch up to four times and report failures to Sentry.

Failed invocations are retained for 14 days, as long as the dead-letter queue keeps the message that refers to them, so every message can still identify its batch's records. Retention is for identifying the affected records; it does not make a replay safe, and the replay deadline alone governs replay. A retained `Transactions` batch includes records that were applied before the failure, and replaying them is skipped only while their `BalanceEvent` markers exist. Each marker expires 7 days after its record was first applied, which is before the failed batch reaches the store, and both S3 lifecycle expiry and DynamoDB TTL deletion run asynchronously, so neither an object's presence nor its age shows that the markers still exist. A record cannot be applied before it is created, so a `Transactions` batch has a replay deadline of 7 days after the earliest `dynamodb.ApproximateCreationDateTime` among its records, less one hour for timestamp rounding and clock skew.

Recovery is manual after the underlying fault is understood. Recovery computes a `Transactions` batch's replay deadline first and refuses the batch once the deadline has passed, whether or not its object still exists; the affected Balances must then be corrected without replaying it. Records of a batch within its deadline, and of an `Attachments` batch, which has no markers, are replayed by a synchronous (`RequestResponse`) invocation of the consumer named by the invocation's `requestContext.functionArn`, or of the consumer ADR 0004 names for a removed one (`PublishStream` for a `Transactions` batch), started before the deadline, which is checked again before any retry; a response with `FunctionError` set, or one whose payload lists any `batchItemFailures`, is a failed replay, and the batch is kept for further recovery. Replayed attachment deletions are harmless if a file is already gone. Batches produced by a data restore, whose event source mappings drop the restore's own records when resumed, must be discarded and never replayed. Each dead-letter queue message is deleted once its batch has been replayed, refused with its Balances corrected, or discarded, and not before. The alarm reports only when the queue stops being empty, so a message left in the queue hides every later failure until it expires after 14 days; a message that arrives during recovery refers to another batch and is handled in the same way.
