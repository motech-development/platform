# Read the Application Table Stream with Two Consumers

The application table stream has two consumers, one in each stack that owns stream work, instead of the six that ADR 0003 kept. AWS recommends designing for at most two readers per shard, and a live Balance took two stream hops to reach subscribers: the `Transactions` consumer wrote the Balance, and a second consumer read that write back from the stream before calling `transactionBeacon`. `ProcessStream` in `accounts-data` maintains derived state: attachment cleanup, typeahead suggestions and scheduled-transaction schedules. `PublishStream` in `accounts-api` is the only consumer that applies Balance changes. It applies each one itself, reads the Balance back with a consistent read and publishes it with `transactionBeacon`, so a saved Transaction reaches `onTransaction` subscribers after one stream hop. It also publishes the transaction-change and notification beacons. A Balance write no longer triggers a publish of its own.

The publisher lives in `accounts-api` because AppSync subscriptions fire only from AppSync mutations, and `accounts-data` deploys first and cannot import the API's URL. Computing the Balance in the AppSync write path was rejected because it would rewrite the VAT and daily-total arithmetic in VTL for three resolvers and the scheduled publisher. An EventBridge Pipe or Kinesis fan-out was rejected because it adds infrastructure, and asynchronous delivery loses per-item order.

Both consumers applied Balance changes until this split had reached production, and a later change then removed the step from `ProcessStream`. `accounts-data` deploys before `accounts-api`, so dropping the step in the same change would have left Transactions saved between the two deployments unapplied for good. Applying from both was safe because a stream record's `eventID` is the same for every consumer and keys the `BalanceEvent` marker, so whichever consumer applied a record first won and the other skipped it. The marker still makes a retried or replayed record apply once, and `PublishStream` still publishes the Balance after a skip.

Both consumers send exhausted batches to the stream-processing failure store from ADR 0002. `ProcessStream` keeps a batch size of 1, which isolated failures in schedule synchronisation. `PublishStream` reports partial batch failures, so a retry resumes at the record that failed. The schedule-synchronisation failure store from ADR 0001 no longer receives batches, and it is removed once its retained objects have expired. A retained batch whose `requestContext.functionArn` names a removed `Transactions` consumer is replayed to `PublishStream`, and one that names a removed `Attachments` or `ScheduleTransactions` consumer is replayed to `ProcessStream`. Only `PublishStream` applies Balances, so every batch replayed to it, including a legacy `Transactions` batch, has ADR 0002's Balance replay deadline; after it, the batch is not replayed and its Balances are corrected. A batch replayed to `ProcessStream` no longer changes Balances, so it has no Balance deadline. A `ProcessStream` batch retained while that consumer still applied Balances is replayed without them: `PublishStream` read the same records, and a Balance it failed to apply is in a batch of its own. While a deployment creates the new mappings before deleting the old ones, a record can be processed by both. That is harmless: every write either consumer makes is idempotent, and the worst case is a beacon published twice.
